# #120 O3: frequency-weighted RAM eviction and a pinned hot set (replay)

`xtask replay` adds two RAM policies:

- **Frequency-weighted eviction.** The victim is the key with the lowest §6.2 score decayed at a long half-life: `freq H=4096`, or `LFU` with no decay.
- **Pinned hot set.** Both tiers are pre-filled from a long-horizon routing profile, as in the pre-fill row, and the top share of each RAM class's slots is then pinned: never a victim. The profile is leave-one-out decode counts from the other traces.

Setup: the m3.7 traces (rt1–4, K 18) and the #147 serve traces (8 turns, K 19). Residency is inclusive, VRAM is LRU, and every run starts cold. d is the share of routed expert bytes read from disk during decode steps; "early" is the first 32 steps of each trace.

## O3 answer

- **Pinned hot set: rejected.** Every pinned share is worse than plain CLOCK on both trace sets and both pool sizes. At 63 GiB, pinning 25% costs +2.7 points on m3.7 and +1.6 on serve. At 50% the cost grows to +5.5 and +3.2.
  - Why: the leave-one-out profile is a poor predictor of the next prompt's hot set. A pinned slot that the next prompt does not route is capacity removed from the pool.
  - The pre-fill row starts from the same warm state but lets the profile be evicted. It keeps the early-window gain (−0.9 m3.7, −2.2 serve at 63 GiB) and loses nothing over the whole run, so the loss comes from pinning itself.
- **Frequency-weighted eviction: a small gain, but below the §6.2 decay already measured.** Long-horizon frequency (H=4096 or LFU) beats CLOCK by 0.1–0.5 points. It loses to decay at H=512 everywhere, and it is worse in the early window (+2.3 points on m3.7 at 63 GiB), because stale counts from the previous phase stick.
- **The policy lever is still about 1 point.** If RAM policy changes at all, decay at H=512 D=0 is still the best single option: −0.8 m3.7 / −0.4 serve at 63 GiB, and −0.7 / −0.2 at 78 GiB. Pool size moves more than any policy: 63 → 78 GiB is −5.3 / −5.6 points.

## `residency.rs:822`: prefill hits set the CLOCK reference bit

`lease_if_resident` (the prefill-stream path) sets the reference bit. Its own doc says a streamed ubatch "must not touch the decode hot set". The replay models prefill as pooled: misses are admitted, as on the non-streamed path. Within that model, the knob `prefill_ref: false` stops prefill RAM hits from setting the bit, which isolates the ref-bit effect only:

| pool | m3.7 d % ref / no ref | serve d % ref / no ref |
|---|---|---|
| 63 | 18.0 / 18.2 | 19.2 / 19.3 |
| 78 | 12.7 / 12.7 | 13.6 / 13.6 |

The code contradicts its doc, but within this model, fixing it does not help: d is unchanged or 0.1–0.2 points worse, and the early window gets worse (+1.8 m3.7 at 63 GiB). The prefill's routed experts are a mildly useful recency signal for the turn's first decode steps. **Not worth fixing first.** The cheaper fix is to correct the doc comment.
