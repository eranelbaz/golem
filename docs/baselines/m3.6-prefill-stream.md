# M3.6 prefill streaming — first real-model measurements

Machine: RX 7900 XTX (24 GiB), 93 GiB RAM, Ryzen 9 9950X3D, model on
nvme0n1 with replica on nvme1n1. GLM-5.3-Flash UD-Q4_K_XL, `--ram-experts-gib
57`, `--ctx 4096`, `--n-predict 1`, manifest on. Every run cold
(`drop_caches` before each). Wall clock includes model load (~10 s).

## Prompt of 582 tokens

| run | flags | device K | wall |
|---|---|---|---|
| on512a | `--prefill-stream --prefill-ubatch 512` | 15 | 114.4 s |
| off512 | (per-token path) | 22 | 223.2 s |
| on512b | `--prefill-stream --prefill-ubatch 512` | 15 | 109.1 s |
| off512b | (per-token path) | 22 | 236.9 s |
| on512c | `--prefill-stream --prefill-ubatch 512` | 15 | 97.4 s |
| on512d | `--prefill-stream --prefill-ubatch 512` | 15 | 94.9 s |
| whole512 | as on512, `--prefill-stream-routed-max 0.001` (every plane whole) | 15 | 110.5 s |

Streamed ≈ 2.1× faster cold (mean 104 s vs 230 s), ≈ 5.6 vs 2.5 prompt
tok/s. Below the design estimate (≈21 tok/s at 512): the reader sustains
≈1.9–2.1 GB/s from disk (measured from `/proc/<pid>/io`), so the stream is
disk-bound, not PCIe-bound. Routed-only vs whole at 512: whole is slower
(110 s vs 95–114 s); every expert is routed at 512 tokens anyway, so the
switch threshold sits below 512 and needs the T = 16/32/64 sweep.

## Prompt of 2,374 tokens

| run | flags | device K | wall |
|---|---|---|---|
| off (smoke) | per-token path, `--n-predict 8` | 22 | 824.0 s |
| on2048 | `--prefill-stream --prefill-ubatch 2048` | 13 | 119.2 s |

≈ 6.9× faster cold (the off run also decoded 8 tokens vs 1; decode is a few
seconds of 824 s); ≈ 20 prompt tok/s streamed vs ≈ 2.9 per-token.

## Output parity

The first sampled token differs between streamed and per-token prefill at
582 tokens (`785` vs `154842`, top-1/top-2 logits 13.95/13.70 vs
13.65/13.63). Streamed whole-plane and routed-only agree bit-exactly with
each other, and the 2,374-token streamed run picks `785`. Likely cause
(unverified): the ubatch shape (one 512-token ubatch vs 2-token per-token
chunks at K=22, top-k 8) selects a different `MUL_MAT_ID` kernel (MMQ vs
vector) and accumulation order. To confirm: an unstreamed run with the
same 512 ubatch on an all-VRAM build. The tiny-moe HIP acceptance test
pins bit-exact parity there.
