# M3.3 store baseline measurements

Config: GLM-5.3-Flash UD-Q4_K_XL, 6 split shards, two nvme replicas
(nvme0n1 Samsung 990 PRO 4TB via btrfs `/home`, nvme1n1 PNY CS2130 1TB ext4
`/mnt/data`), 24 GiB VRAM, 93 GiB RAM.
Engine: this branch (`26-taskm33-store-wiring`, golem-store shared-queue
striping); fork commit per `vendor/VENDOR_SHA`.
Bench: `read_bench` example — 200 × 5,898,496 B plane reads through the
ChunkQueue, seeded scattered offsets (cold without root `drop_caches`:
different seeds touch disjoint file regions and O_DIRECT never populates the
page cache). Single reader thread per physical drive (§5.2, D-12 default).

## Measurement-hygiene findings (fixed before recording)

- `read_bench` originally passed a plain `Vec<u8>` destination: its base
  pointer is not 4 KiB-aligned, so **every** chunk silently took the
  buffered+`DONTNEED` fallback (§5.4 alignment rule). Early A/B numbers were
  page-cache artifacts (73 µs per 2 MiB chunk = memcpy, not disk). The
  example now over-allocates and slices to an aligned address; per-replica
  `direct:`/`buffered:` counters are printed so this cannot recur silently.
- `--io-threads 2` (two reader threads per drive) **regresses**: 0.70 GB/s
  combined, 0.25 GB/s on nvme1n1 alone — reproduces M0's t8 finding that
  these drives lose throughput under concurrent O_DIRECT. The 1-thread-per-
  drive default stands.

## 1. Bandwidth A/B — one drive vs both (`read_bench`, O_DIRECT, cold)

O_DIRECT reads never populate the page cache, so seeded-scattered runs are
cold by construction; warm-vs-cold is therefore not meaningful per leg and
is not faked. §12.3 order A-B-B-A.

| Order | Config | GB/s | ms per 5.9 MB plane | ms per 15.2 MB unit (extrapolated) | Fast-drive chunk share |
|---|---|---|---|---|---|
| A1 | nvme0n1 alone | **4.97** | 1.19 | 3.1 | — |
| B1 | both drives | **4.73** | 1.25 | 3.2 | 66.7% |
| B2 | both drives | **4.73** | 1.25 | 3.2 | 66.7% |
| A2 | nvme0n1 alone | 3.63–4.10 | 1.4–1.6 | 3.7–4.2 | — |

Sequenced-sequential variant (`--sequential`, the real page_in access shape:
a cold layer's planes are contiguous per shard): A 3.14 GB/s, B(nvme1)
1.73 GB/s, both **4.30 GB/s**.

nvme1n1 alone: 1.74 GB/s (scattered) / 1.73 GB/s (sequential) — consistent
with M0's 2.24 GiB/s sequential minus seek cost across 6 shard files.

### Arithmetic against the plan target

Plan target: ≈1.76 ms/unit (8.64 GB/s combined) vs 2.44 ms/unit fast-drive-
alone. Measured: **3.2 ms/unit combined vs 3.1 ms/unit fast-drive-alone**.

Why the gap: the plan's 8.64 GB/s assumed M0's deep-queue sequential rates
(5.81 + 2.24 GiB/s). The P3 queue is QD1 per drive by design (D-12: more
threads/drive regresses — re-measured above), and QD1 O_DIRECT delivers
~3–5 GB/s on nvme0n1, not 5.8. Work-conserving striping across two QD1
drives gives makespan ≈ total/(r₀+r₁) — the drives do run concurrently
(per-chunk traces show interleaving), and combined throughput exceeds the
fast drive alone on the mixed pattern (4.73 vs A-leg average ≈4.3). The
faster drive self-selects proportionally to per-chunk latency (measured
shares match the 0.7 ms : 1.2 ms per-chunk-time ratio ≈ 63:37; uniform split
would be 50:50, static round-robin is what the pre-fix code did).

Follow-up (recorded, not fixed here): per-drive queue depth is the remaining
lever and is bounded by the t8 regression; io_uring (R-17) stays out of v1.

## 2. Page-cache non-growth

`/proc/meminfo` `Cached` before/after 3 × 300 plane reads (≈1.7 GB) through
the queue, all-O_DIRECT, both drives:

| Config | Cached before | Cached after | Δ |
|---|---|---|---|
| both drives, O_DIRECT | 37,932,612 kB | 37,942,248 kB | **+9 MB** (noise) |

H-9 holds: expert bytes do not populate the page cache. Buffered-fallback
DONTNEED: verified by unit test (`fallback_reads_invoke_dontneed`); no
fallback occurred during these bench runs (all chunks `direct:`).

## 3. Failover demo

Executed live (#66), procedure `docs/procedures/m3.3-failover.md`, commit
`e5b89dc` release HIP build on nvme0n1. Decode: `--n-gpu-layers 99
--cpu-moe-layers 99 --greedy --ctx 1024 --n-predict 512 --ram-experts-gib 8
--device-cache-experts 10 --manifest` (small pool on purpose: 8 GiB / 15.2
MB unit ≈ 560 expert slots vs 12,096 experts (42 × 288), so expert reads stay on disk). At
≈ token 100 (stdout ≥ 400 B) `echo 1 > /sys/block/nvme1n1/device/device/remove`.

| | tokens | tok/s | MB/token |
|---|---|---|---|
| before removal | 0–99 | 0.73 | 3,028 |
| first 40 after | 100–139 | 1.34 | 2,946 |
| rest | 140–510 | 1.25 | 3,183 |

- Decode ran to completion (rc 0, 511 steps, 462 s), no read error
  surfaced. tok/s rose after removal: the first 100 include cold dense
  weight and pool fill, so the post-removal rate is the survivor alone.
- `/proc/diskstats` sectors read: 10 s before removal nvme0n1 +19.9 M,
  nvme1n1 +23.6 M (both drives serving); 10 s after nvme0n1 +77.0 M, nvme1n1
  gone — reads moved entirely to the survivor.
- Health transition warn: **not captured**. The `golem` binary installed no
  tracing subscriber, so `tracing::warn!` from the store was dropped.
  Fixed in this change (`golem-cli` now initialises `tracing-subscriber`,
  warn default, `RUST_LOG` override); the transition itself is unit-tested
  (`store_source.rs`). Re-capture needs another device removal.
- Recovery: `umount -l`, PCI rescan, `mount` → nvme1n1 back, ext4 "recovery
  complete", no errors. The desktop session crashed shortly after recovery
  while a replica byte-compare and a release build ran concurrently; cause
  not isolated.

## 4. Cold decode tok/s, manifest vs plain GGUF (#66)

`scripts/ab-manifest-ab.sh` (A = plain GGUF, B = `--manifest`), orders
A B B A + B A A B, every leg cold (`drop_caches`), `GOLEM_AB_GIB=57`, ctx 1024,
128 tokens, release HIP build at `e5b89dc`. All 8 outputs byte-identical.

| leg | tok/s | disk GB/token |
|---|---|---|
| 1 plain | 2.619 | - |
| 2 manifest | 2.327 | 1.15 |
| 3 manifest | 2.357 | 1.15 |
| 4 plain | 2.615 | - |
| 5 manifest | 2.352 | 1.15 |
| 6 plain | 2.617 | - |
| 7 plain | 2.618 | - |
| 8 manifest | 2.380 | 1.15 |

Plain 2.617 ± 0.002 tok/s, manifest 2.354 ± 0.022: the store path is
≈ 10% **slower** on this workload. The plain leg reads experts through the
GGUF mmap/pread path; the store path O_DIRECT-reads 1.15 GB/token through
the two-drive queue. At 128 tokens most of a 57 GiB pool fill is in the
window, so this is a cold-fill comparison, not steady-state. The
`unmeasured` store counters on the plain leg are why `disk GB/token` is
blank there. Warm legs not run: expert reads are O_DIRECT and every
process starts with an empty pool, so warm differs only in dense-weight
page-cache state (see `ab-bench.sh`).
