# M3.9 — CPU expert-math microbench (plan step 1, option b)

**Date:** 2026-10-06 · **Machine:** AMD Ryzen 9 9950X3D (16C/32T), dual-channel DDR5-6000 (≈96 GB/s theoretical), no GPU involved.
**Method:** vendored llama.cpp `test-backend-ops` in **perf** mode, CPU backend only. Stock cases do not cover the GLM expert shapes, so a scratch copy of `tests/test-backend-ops.cpp` (untracked, in the build dir) adds:

- `MUL_MAT_ID` GLM cases: `n_mats=288, n_used=8 (top_k), n=1 token`, type_b=f32, plane shapes from the real GGUF header: gate/up `(4096, 2048, 288)` → k=4096, m=2048; down `(2048, 4096, 288)` → k=2048, m=4096. `op_flops=0` + `op_size` counting **only the 8 routed experts** (not all 288) so perf mode reports touched-bytes GB/s.
- `MUL_MAT` shared-expert (`shexp`) cases at `(4096,2048)` / `(2048,4096)`, n=1, same bandwidth treatment.

Real types read from `GLM-5.3-Flash-UD-Q4_K_XL` GGUF headers (gguf-py): gate/up_exps are a per-layer mix of **Q4_K / Q5_K**, down_exps a mix of **Q5_K / Q6_K**; both plane geometries are 8,388,608 elems/expert (Q4_K 4.72 MB, Q5_K 5.77 MB, Q6_K 6.82 MB). Each type is benched separately; the blend below assumes 50/50 within each plane pair (the per-layer mix varies; no per-layer weights recorded).

Build: `/mnt/data/golem/llama-cpu-bench` (cmake Release, `-DGGML_HIP=OFF -DLLAMA_BUILD_TESTS=ON`, static), binary `scratch/test-backend-ops-glm` (scratch TU + built ggml static libs; `GOLEM_BENCH_N_THREADS` env selects thread count). Threads were pinned cold per run; each case runs a ≥1 s timed loop (7k–100k iterations). Nothing committed.

## Blended routed-expert rate

Per expert: gate+up = 2 planes at (Q4_K+Q5_K)/2 = 5.24 MB/plane, down = 1 plane at (Q5_K+Q6_K)/2 = 6.30 MB → 16.79 MB/expert. Bytes-weighted CPU rate:

- **8 threads:** (10.49 MB × ~240) + (6.30 MB × ~149) → **≈205 GB/s** (≈8 µs/expert, 8 experts ≈ 66 µs/layer)
- **32 threads:** ≈400+ GB/s (compute-bound territory; steals cores from engine/DMA)
- **1 thread:** ≈30 GB/s (Q6_K 43, Q4_K 32)

This replaces §2.4's unmeasured "CPU 20–41 GB/s" K-quant rate. Even granting heavy degradation from concurrent PCIe DMA + disk traffic (the §2.4 pessimism factor, solo→concurrent ≈ ½), the CPU leg has ≥100 GB/s of headroom over its assumed 41.

## Verdict vs the #52 gate (d ≤ ≈0.1)

- Measured CPU K-quant rate **(~205 GB/s @ 8 threads, ≈30 @ 1 thread)** is ~5× the 41 GB/s §2.4 assumed → the CPU-math side of #52 is cheap and would not throttle decode.
- But the gate is about **d, not CPU speed**: d ≈ 0.22 at the feasible 59–63 GiB pool (d ≈ 0.094 needs a 90 GiB pool — infeasible). At d = 0.22–0.14 the split buys +7–15%, capped by disk, not by CPU math.
- **Gate still not met.** Measuring the CPU rate was the last unknown (plan step 1); it does not change the gate outcome — it strengthens it, by showing the CPU leg would never be the bottleneck even if built. Decision stays with the user per plan §0: defer #52 until #64 (+ #49) lands and re-measure d.

## Caveat: cache-hot rates

`test-backend-ops perf` re-runs the same 8 experts, ≈40 MB per plane type,
which fits the 9950X3D's 128 MiB L3. The rates above are compute-bound
ceilings, not pool rates: decode streams fresh experts from DRAM, and
dual-channel DDR5 caps that near 60–80 GB/s, shared with the H2D DMA.
Using 60 GB/s instead of 205 GB/s still makes the CPU term smaller than
the disk term at d ≥ 0.14, so the verdict holds: disk bytes bound the
split, the d ≈ 0.1 gate is not met, and #52 stays gated until #64/#49
move d.
