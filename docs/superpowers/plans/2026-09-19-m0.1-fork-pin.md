# M0.1 Fork Pin — Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Vendor the llama.cpp fork that carries GLM-5.3-Flash (`glm5next`) support at a pinned commit into `vendor/llama.cpp/`, record the pin in `engine/llama-cpp.lock` + `docs/adr/0001-fork-pin.md` (design §3.2, worklog M0.1), and amend the design docs to match the as-vendored reality.

**Architecture:** No Rust code changes. The fork is vendored as plain files under `vendor/llama.cpp/` (single squashed commit in the golem repo — no nested `.git`, no submodule). The pin is verified by a **recomputable content-manifest hash** with ONE canonical command, used verbatim everywhere (fingerprint, verification, CI, ADR re-vendor procedure):

```bash
(cs() { cd "$1" && find . -path ./.git -prune -o -type f -print0 | LC_ALL=C sort -z | xargs -0 sha256sum | sha256sum | awk '{print $1}'; }; cs DIR)
```

The `cd`-inside + `find .` form and `LC_ALL=C` are load-bearing: `sha256sum` output lines include filenames, so a repo-root invocation (`find vendor/llama.cpp …`) hashes a different path prefix than a /tmp one and the hash can never match across locations; `sort` order is locale-dependent and would diverge between dev machine and CI. The hash is recorded in `vendor/VENDOR_SHA` (outside the vendored tree, bare `key=value` lines, no inline comments) and in the lock; a CI job re-derives it with the identical command on every push. Because the pin lives on a mutable third-party fork's draft PR, a pristine tarball is parked at `~/.cache/golem/vendor/` (durable across reboots, unlike `/tmp`), and the branch is pushed to origin immediately after vendoring (the pushed commit is itself a durable copy). All fidelity gates run against the **git index after `git add -f`** — not just the working tree — because both the vendored upstream `.gitignore` and golem's root `.gitignore` (`models/`, `*.gguf`) would otherwise silently strip vendored files between verification and commit. The design docs (§3.2 lock template + acceptance, §3.5 ROCm line, §13 vendor-layout comment, §14), the worklog's M0.1 and M0.2 task lines, and `product-spec.md` are amended in this same PR — log notes are not spec changes.

**Tech Stack:** git, GitHub API (`gh`), plain markdown files. No build in this task (M0.2 builds it).

**Spec:** `docs/tech-design.md` §3.2 (the fork), §14/M0.1; `docs/worklog.md` M0.1; `product-spec.md`.

- [ ] **Step 1: Fingerprint the pristine tree BEFORE any transfer**

```bash
cd /tmp/golem-vendor-tmp
git checkout "$PIN" -- .   # populate the worktree
cs() { cd "$1" && find . -path ./.git -prune -o -type f -print0 | LC_ALL=C sort -z | xargs -0 sha256sum | sha256sum | awk '{print $1}'; }
CANON=$(cs /tmp/golem-vendor-tmp)
# Canary: the canonical recipe MUST reproduce itself before it is trusted anywhere:
test "$CANON" = "$(cs /tmp/golem-vendor-tmp)" || { echo "CANONICAL HASH NOT STABLE — stop, fingerprint is broken"; exit 1; }
fc=$(find . -path ./.git -prune -o -type f | wc -l)
{ echo "content_sha256=$CANON"; echo "file_count=$fc"; echo "commit=$PIN"; \
  echo "# archive_sha256 (provenance only, dies with the tarball): $(git archive HEAD | sha256sum | awk '{print $1}')"; } > /tmp/golem-vendor-fingerprint
cat /tmp/golem-vendor-fingerprint
mkdir -p ~/.cache/golem/vendor
tar --exclude-vcs -czf ~/.cache/golem/vendor/golem-vendor-tarball.tar.gz -C /tmp golem-vendor-tmp  # durable recovery source (NOT /tmp)
```

`content_sha256` is the load-bearing anchor: repo-independent, recomputable from the vendored tree forever with the identical `(cd … && find . … | LC_ALL=C sort -z …)` form. `archive_sha256` is kept as a tarball-era provenance note only — it dies with the tarball. `VENDOR_SHA` format contract (ADR): bare `key=value` lines, comments on their own `#` lines, no inline comments.

name: vendor-pin-check
