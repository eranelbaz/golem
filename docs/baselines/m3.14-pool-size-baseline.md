# M3.14 pool-size baseline measurements (10/40/63 GiB)

Config: GLM-5.3-Flash UD-Q4_K_XL, 6 split shards, two NVMe replicas per
manifest, 24 GiB VRAM, 93 GiB RAM, host omarchy.
Model:
`/home/eranelbaz/models/glm-5.3-flash-ud-q4k-xl/UD-Q4_K_XL/GLM-5.3-Flash-UD-Q4_K_XL-00001-of-00006.gguf`
Manifest: `/home/eranelbaz/models/glm-5.3-flash-ud-q4k-xl/UD-Q4_K_XL/manifest.json`
Commit under test: `612d86bc3b6ca2fe2d37ea80197176cacbca3307`.

Expert-byte arithmetic: 42 MoE layers × 288 experts × 3 planes =
12,096 expert units; × ~15.34 MB per unit = 172.8 GiB total expert bytes.
(The plan's 15.2 MB figure is a rounded value; 15.34 MB is the measured
per-unit byte count from the manifest, used throughout.)

Per-leg command line (identical for all pool legs, `--ram-experts-gib` varies):

```
golem --n-gpu-layers 99 --cpu-moe-layers 99 --greedy --ram-experts-gib {10,40,63} \
  --timing-csv <leg>/timing.csv \
  --manifest /home/eranelbaz/models/glm-5.3-flash-ud-q4k-xl/UD-Q4_K_XL/manifest.json \
  --prompt .m14-work/prompt.txt
```

Prompt: a repeated harbor-town paragraph plus "Continue the story."
(`.m14-work/prompt.txt`). The engine does not log a prompt-token count
(`prompt_tokens=unknown` in every `meta.txt`); 63 decode rows per leg for
`predict=64` imply ~1 prefill token, so tok/s is effectively decode-only.

Pool sizes: 10 / 40 / 63 GiB.

- **Cold** = all 6 shards evicted from the page cache via
  `scripts/evict-model-cache.py` (posix_fadvise DONTNEED) immediately before
  the run. Expert reads use O_DIRECT and never populate the page cache, so
  cold/warm differs only in the non-expert (dense weights, KV scratch, mmap)
  load path.
- **Warm** = immediate re-run, page cache as left by the cold leg.
- **Pool-warm is not measured**: every leg is a one-shot first-turn in a
  fresh process, so the pool starts empty in all legs.

Order disclosure: ascending (10→40→63) then descending (63→40→10), one run
each direction per temperature. Single-run numbers — no repeats; variance is
not separately quantified.

(arithmetic: means of the per-leg table rows per size. Asymmetry disclosure:
the 40 and 63 GiB warm means are 2-leg means (asc + desc); the 10 GiB warm

Core scaling result: decode tok/s is monotone non-decreasing in pool size
across cold means (0.633 → 1.430 → 2.580) and mean disk share is strictly

designed.

Warm-vs-cold inversions (desc order at all three sizes, e.g. desc-40-warm
1.153 < desc-40-cold 1.448 tok/s) are within single-run variance given the
disk-share overlap between the two temperatures; no repeats exist to resolve
them.

## 3. §2.4 predicted vs measured — the model misses by +27% to +103%

The §2.4 serial model predicts `t = max(R/X, D/4.73) + D/X` with X = 27 GB/s
(pin bandwidth), D = disk GB/token, R = remaining expert bytes/token served
from the pool. Measured `d` per leg; total expert bytes 172.8 GiB =
12,096 units × 15.34 MB.

Byte-ratio expectations: 10/172.8 = 5.8%, 40/172.8 = 23.1%, 63/172.8 = 36.5%
of expert bytes served from disk per token at steady state. Measured shares
(16.6–79.2%) are well above these one-epoch figures because a 64-token
generation routes far more than one epoch of experts.

Every leg is flagged. Analysis of the miss, without fabricating a split:

- H2D time is inside the compute column (`h2d_ms` literal `unmeasured`), so
  the measured excess over prediction could be effective H2D bandwidth below
  the 27 GB/s pin assumption, disk bandwidth below the 4.73 GB/s § m3.3
  figure, or both. The data does not separate them.
- Disk ms share >100% (e.g. asc-10-warm 169.2%) shows per-drive workers
  sustain read bandwidth comparable to the serial model's assumption yet the
  legs still run slower — i.e. serialized waiting on expert reads, not raw
  read bandwidth, dominates decode. The §2.4 model's serial shape
  (`max(R/X, D/4.73) + D/X` treating pool-hit time as free) is the likely
  wrong term: R is charged nothing, yet pool-hit legs still spend ~48–50%
  of wall in compute + H2D.
- No split between H2D and disk is claimed beyond this.

## 4. H2D `unmeasured`

`h2d_ms`, `h2d_bytes`, `policy_ms` are literal `unmeasured` in the timing CSV
(fork event pair pending, `crates/golem-engine/src/timing.rs:20-24`), so
`compute_ms` is derived by subtraction and **contains H2D time**. All
"compute + H2D" columns in this doc include H2D; a clean H2D split is
deferred until the fork event pair lands.

## 5. 63 GiB preflight-cap arithmetic and 70 GiB safety

`preflight_ram_pool` (`crates/golem-cli/src/run.rs:186-232`) refuses a pool
wanting more than available × 3/4. 63 GiB therefore needs ≥ 63/0.75 = 84 GiB
available. At run time the guard reportedly fired twice at 83 GiB available
and legs started only after `sync && echo 3 > /proc/sys/vm/drop_caches`
(legs that needed the drop: asc-63-cold, asc-63-warm, desc-63-cold,
desc-63-warm, probe-63-cold). Evidence caveat: no artifact of these guard
firings survives — they were observed only in the coordinator session
history, and the leg logs do not record preflight refusals.

70 GiB needs 70/0.75 = 93.4 GiB available > 93 GiB physical ⇒ **not
startable** without a code change to the 3/4 ceiling.

Safety arithmetic for 63 GiB locked pool: 63 GiB (mlocked) + ~11 GiB
non-expert RSS + a few GiB desktop = ~76 GiB of 93 GiB ⇒ ~17 GiB headroom.
PSI/vmstat during probe-63-cold pool fill (5 samples, 01:46–01:48): PSI
some/full avg10 = 0.00 across all samples, vmstat `si` = 0, MemFree dropped
90.3 GB → 8.3 GB as the 63 GiB pool populated (sample 1: 90,312,976 kB free;
sample 5: 8,259,680 kB). Zero reclaim pressure, zero swap-in.

Verdict: 63 GiB is safe on this machine. **Recommendation** (no code change
made): a modest raise of the preflight ceiling (e.g. allow want ≤ available ×
0.75 but also accept want ≤ physical − fixed reserve) would let 63 GiB start
without `drop_caches`; 70 GiB would additionally need the physical-reserve
check to replace the pure ratio check.

Gap disclosure: the PSI probe's decode-phase samples are missing — the
sampling loop ended early, so the evidence covers pool fill only, not decode.

## 6. Incident disclosure

The first asc-10-cold attempt GPU-hung: `HW Exception ... GPU Hang`; the
kernel logged a successful GPU reset followed by `device wedged` and
`MES failed to respond` ×4, and the desktop destabilized. After reboot, the
identical leg passed clean and all 12 legs + the probe completed hang-free.
Treated as a prior-wedged-state artifact; not reproduced. Evidence caveat:
the failed attempt's stdout.log was overwritten by the clean rerun; the hang
text quoted above comes from the coordinator session record, not a surviving
log file.
