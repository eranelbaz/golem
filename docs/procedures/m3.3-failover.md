# M3.3 live failover procedure (design §5.4)

Two-drive replica read with a live drive failure: chunk requeue with the
failed replica excluded, one-way `Healthy → Degraded` marking, decode
continues off the surviving drive.

## Preconditions

- Replicas of the target shard exist on **both** drives (`golem import`
  done; `lsblk -f` confirms nvme0n1 and nvme1n1 are distinct physical
  devices, no §5.1 shared-device warning at startup).
- Root (sudo) access for the sysfs failover/injection steps. Only these
  commands are passwordless (`NOPASSWD` in sudoers); anything else asks for
  a password or fails:

  ```text
  tee /proc/sys/vm/drop_caches
  tee /sys/block/nvme1n1/device/device/remove
  tee /sys/class/nvme/nvme1/rescan
  tee /sys/bus/pci/rescan
  umount -l /mnt/data
  mount /mnt/data
  ```
- **Safety: never remove the drive hosting `/` or `/home`.** Confirm with
  `lsblk -f` / `findmnt /` that nvme1n1 is the expendable data drive before
  step 3. Double-check the device name; `remove` is irreversible for the
  session.
- `golem` built from the PR commit under test; `RUST_LOG=warn` (or finer)
  so tracing transitions are visible.

## Steps

1. Start decode against the manifest with replicas on both drives:

   ```bash
   golem run --manifest /home/eranelbaz/models/glm-5.3-flash-ud-q4k-xl/UD-Q4_K_XL/manifest.json \
       --ram-experts-gib 4 \
       /home/eranelbaz/models/glm-5.3-flash-ud-q4k-xl/UD-Q4_K_XL/
   ```

2. Begin decode; confirm steady-state reads are striped across both drives
   (run-log disk GB/s roughly double the single-drive rate).

3. Fail the drive — software-equivalent of a physical yank:

   ```bash
   echo 1 | sudo tee /sys/block/nvme1n1/device/device/remove
   ```

   This is the PCI-level equivalent of pulling the device; in-flight I/O
   returns EIO/ENODEV exactly as on a physical unplug.

## Expected behavior

- Failing chunk reads requeue drain-locally with the nvme1n1 replica's
  exclude bit set (§5.2); a healthy replica serves them — no hang, no
  failed read surfaced while nvme0n1 is healthy.
- The nvme1n1 replica slot is marked `Degraded` (one-way, §5.4).
- Health transitions logged via `tracing::warn!`, message "store instance
  health transition (§5.2/§11)" with `from = Healthy`, `to =
  DegradedReplica` (Debug field formatting).
- Decode continues, now bounded by nvme0n1 alone (≈2.44 ms/unit vs
  ≈1.76 ms/unit striped; see `docs/baselines/m3.3-store-bench.md`).
- Paste the actual log lines and transition into
  `docs/baselines/m3.3-store-bench.md` and the PR body.

## Recovery

```bash
# device/device/remove drops the PCI function, so /sys/class/nvme/nvme1
# is gone. The stale /mnt/data mount (now pointing at a dead device) must
# be lazily unmounted before the rescan; a PCI bus rescan re-enumerates it:
sudo -n umount -l /mnt/data
echo 1 | sudo -n tee /sys/bus/pci/rescan
lsblk   # confirm nvme1n1 is back
sudo -n mount /mnt/data
```

Then re-import / verify the replica (`golem import` against the recovered
device) and restart (or re-open) the run; health returns to `Healthy` on
the next successful open. A `Degraded` slot is one-way within a run by
design (§5.4) — recovery is a fresh open, not a flag flip.

Exact commands for the #66 evidence run. HAZARD first (see the plan,

#                and /mnt/data/golem/models/GLM-5.3-Flash-GGUF/UD-Q4_K_XL

**F2 — start decode** (long prompt, n ≥ 512 tokens, so decode outlasts

  --manifest /home/eranelbaz/models/glm-5.3-flash-ud-q4k-xl/UD-Q4_K_XL/manifest.json \

In a second terminal, confirm both drives read:

```bash

```

**F3 — fail the drive at ~token 100:**

```bash
date +%s.%N
echo 1 | sudo -n tee /sys/block/nvme1n1/device/device/remove
```

**F4 — observe:** the `tracing::warn!` "store instance health transition
(§5.2/§11)" `from=Healthy to=DegradedReplica` line; no read error
surfaced; the timing CSV keeps producing rows. Let decode finish; record
tok/s before/after the event from the CSV.

**F5 — recover:**

```bash
sudo -n umount -l /mnt/data
echo 1 | sudo -n tee /sys/bus/pci/rescan
lsblk                       # nvme1n1 must reappear
sudo -n mount /mnt/data
git -C /mnt/data/golem/wt64 status   # sanity
dmesg | tail                # no fs errors
```

If ext4/xfs reports errors, stop and ask the user before any fsck.

**F6 — replica verify:**

```bash
golem import verify ...   # or sha256sum -c against the replica's sha256s.txt
```

Then paste the log lines + CSV excerpt into
`docs/baselines/m3.3-store-bench.md` §3.

## Teardown

- Stop `golem run` (Ctrl-C).
- If the device was removed, `rescan` per above; confirm with `lsblk`.
- Nothing else to revert: the procedure does not touch sysctl state.

## Safety notes

- `device/device/remove` power-cuts the block device at the driver level.
  Any filesystem still mounted from it will go read-only/error; that is why
  replicas live on a dedicated data drive.
- Run the failover at most once per session; repeated remove/rescan cycles
  can leave the NVMe controller in a state requiring a host reboot.
